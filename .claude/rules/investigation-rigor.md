# Investigation Rigor — 除錯與調查的紀律

遇到 bug、測試失敗、非預期行為時的強制規範。

---

## 核心原則

**先找 root cause，再談修法。** 不允許以下行為：

- try-catch 吞錯讓錯誤「消失」
- 靠重試 / reload / 清快取「繞過」問題
- 直接改掉觸發錯誤的那行，不問「為什麼會這樣」
- 同樣的修法重試 2 次以上

---

## 四階段除錯法

### 1. 重現（Reproduce）

- 找出穩定重現的最小步驟
- 明確區分「偶發」與「必現」，偶發優先找競態條件、race condition、外部依賴
- 記錄 console log / network / 畫面狀態（screenshot）

### 2. 定位（Localize）

- 縮小到「最後一個正常的點」與「第一個異常的點」
- 用 `git bisect` 找出是哪個 commit 引入（若是回歸）
- 讀程式碼與 stack trace，不先猜

### 3. 假設與驗證（Hypothesize & Verify）

- 寫下「我認為原因是 X，因為 Y」
- 做**最小實驗**驗證（print、斷點、改一行）
- 實驗結果若與假設不符 → 假設錯，重新提出，不要硬凹

### 4. 修復（Fix）

- 確認真正原因後才動工
- 修完自問：**這個修法處理的是症狀還是原因？**
- 若是症狀，註明 TODO 並回報使用者

---

## 2 次法則

同一問題、同一思路修 2 次都不通 → **停下來**。

不要第 3 次重試。改做：

1. 把當前理解寫下來（文字化逼自己釐清）
2. 重新質疑最初假設是否正確
3. 讀原始碼、查文件、grep 相似案例
4. 必要時回報使用者，描述已嘗試的路徑

---

## 禁止的反模式

| 反模式 | 為何不行 |
|--------|---------|
| `try { ... } catch {}` 空吞錯 | 錯誤會累積直到爆炸 |
| `// @ts-ignore` / `eslint-disable` | 關警示而非解決根因 |
| 無條件 `setTimeout` 拖延 | 掩蓋時序問題，不解決 |
| 改 node_modules 內檔案 | 升級就會被覆蓋 |
| 加「暫時」的 workaround 不開 issue 追蹤 | 暫時一定變永久 |

---

## 修完後的自我檢查

- [ ] 能用一句話說明「為什麼會壞」、「為什麼這樣修會對」
- [ ] 新增 / 修改一個測試防止回歸
- [ ] commit message 的 body 寫清楚原因（不只是「fix bug」）
- [ ] 若涉及共通模組，思考是否其他地方有同類問題

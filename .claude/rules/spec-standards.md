# Spec Standards — 改動前的意圖宣告

> 避免 AI 在沒對齊需求下就動程式碼，導致做完才發現「不是我要的」。

---

## 適用範圍

### 必須寫 spec

- 新增功能（feat）
- 改動超過 3 個檔案的重構
- 牽動 Redux slice / saga 結構
- 牽動路由、身分驗證、金流邏輯
- 牽動外部 API 合約（backend、Firestore 結構）

### 可省略 spec

- 單檔 typo / 文案修正
- 樣式微調（無 RWD 影響）
- 相依套件 patch 升級
- 文件更新

---

## Spec 最小模板

對話或 PR 描述內包含以下五段即可，不必另開檔：

```
## 動機
<一句話，為何要做這件事>

## 目標
<做完後使用者 / 系統看到什麼變化；可驗收標準>

## 非目標
<此次刻意不做的事，避免 scope 膨脹>

## 改動範圍
<預計動哪些檔案 / 模組；風險在哪>

## 測試方式
<手動路徑 / 自動化測試 / 如何確認沒有 regression>
```

---

## 撰寫原則

1. **先寫 spec 再動程式**。寫到一半發現想不清楚 → spec 本身就不對，不是你不會寫 code
2. **非目標比目標重要**。明確排除掉「順手做」的誘惑
3. 任何超出 spec 的改動 → 先停下來問使用者，不要自作主張擴大範圍
4. AI Agent 讀到需求不明確時**必須**先問，勿猜測使用者意圖

---

## 反模式

| 反模式 | 後果 |
|--------|------|
| 「順便把 X 也修了」 | PR 失焦、review 困難、風險擴大 |
| 沒寫非目標就開工 | 做到一半 scope 失控 |
| 只寫「做什麼」不寫「為何」 | 半年後自己都不記得動機 |
| 用 spec 取代程式碼註解 | spec 是需求層，註解是實作層，不互換 |
